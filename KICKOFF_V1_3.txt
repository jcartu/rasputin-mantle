27B ORCHESTRATOR RULES (READ docs/27B_ORCHESTRATOR_GUIDE.md FOR FULL VERSION)
═══════════════════════════════════════════════════════════════════════════════

Short version of what's different from Opus-driven runs:

  1. **Smaller phase scope.** Each W phase has 4-6 tickets MAX. If a phase needs
     more, split into sub-phases (W4a, W4b). This keeps state in YAML, not in
     your head.

  2. **MAX_AUDIT_ITERATIONS = 3.** Hard cap. Drift on 27B compounds across
     iterations; fail fast and surface to user.

  3. **Default concurrency = 4** for executor dispatch. NOT the OMO default of 5.
     One less thing to track.

  4. **Self-check ritual every 5 tickets:**
        $ python3 scripts/sisyphus-state-check.py
     This reads boulder.json + git tags + recent commits and reports any drift
     between what you THINK has happened and what actually has. If drift > 0,
     stop and reconcile before continuing.

  5. **Fallback chain enabled.** oh-my-opencode.json should have:
        sisyphus.fallback_models: ["anthropic/claude-opus-4-7"]
     If 27B rate-limits or returns gibberish, OMO automatically bounces this
     specific turn to Opus. You won't see it; the build continues.

  6. **Explicit state, no inferred state.** When you write a ticket file, the
     ticket file is the source of truth. Don't say "I already updated this" in
     chat without writing it to disk. 27B's "I remember" is unreliable.

  7. **Push every 3 commits.** Same as Opus runs, but tighter — your git state
     should always be < 3 commits ahead of origin.

THE NEW PROGRAMMATIC AUDITOR (NON-NEGOTIABLE)
═══════════════════════════════════════════════════════════════════════════════

in auditor-strict.md enforce this programmatically.

that didn't exist in code. v1.3 cannot ship overclaims — the script catches them
in seconds.
